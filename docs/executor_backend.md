# Подключение бэкенда исполнителя

Мок-данные остаются в `lib/shared/data/demo_store.dart`. `DemoStore` реализует
`ExecutorRepository`; мастер и исполнитель используют один экземпляр хранилища.
Экран исполнителя, карточка, форма закрытия, результаты, профиль и таймер зависят
от интерфейса репозитория, а не конкретного демохранилища.

## Точка подключения

Создать API-адаптер `ChangeNotifier implements ExecutorRepository` и передать его
в `ExecutorScreen` в `lib/app/app.dart`. При входе передавать ID авторизованного
сотрудника: `pushNamed('/executor', arguments: employeeId)`. Без аргумента в демо
используется сотрудник №1. Бэкенд обязан проверять роль и принадлежность наряда;
фильтрация в приложении не заменяет авторизацию.

## Контракт

- `employee`, `assignedTo` — профиль и локальный снимок назначений, включая бригаду.
- `refreshExecutor` — загрузка профиля, нарядов, справочников и результата.
- `isLoading`, `loadError` — состояния загрузки и ошибки; после изменения вызывать
  `notifyListeners`. Существующий снимок сохранять при ошибке обновления.
- `executorAction` — асинхронная смена статуса, с обязательной причиной отказа/паузы.
  Время события и автора подтверждает сервер. Исполнитель не может закрывать наряд.
- `submitExecution` — асинхронная отправка `ExecutionDraft`. Повторный запрос должен
  быть идемпотентным; сервер проверяет актуальную версию наряда, шифр, материалы,
  количества и фото, возвращает обновлённый наряд со статусом `review`.
- `executorFaultCodes`, `executorMaterials` — справочники; сейчас тестовые значения.
- `executionDraft`, `saveExecutionDraft`, `clearExecutionDraft` — черновик по ID
  сотрудника и номеру наряда. В приложении нативных платформ подключён `FileExecutionDraftStorage`: черновик и
  фото сохраняются в каталоге поддержки приложения, восстанавливаются после перезапуска.
  Записи выполняются последовательно через временный файл и переименование.
  `DemoStore` без переданного хранилища и веб-демо используют память.
  После успешной отправки черновик удаляется; данные разных сотрудников разделены.
- `executorRating` — nullable `ExecutorRating`; отсутствие означает ожидание данных.
- `WorkOrder.assessment` — nullable `ExecutionAssessment`, заполняется из ответа
  сервера; новая отправка отчёта сбрасывает старое заключение.

Пока строки справочников используются как значения. При согласовании API заменить
их стабильными ID с отдельными названиями и единицами измерения. `ExecutionDraft`
уже хранит материалы с количеством отдельно; устаревший текст сохраняется в
`legacyMaterials`, чтобы не терять существующие мок-отчёты.

## Синхронизация, уведомления и фото

WebSocket/опрос обновляет снимок репозитория и вызывает `notifyListeners`.
`WorkOrder.history` должен содержать `status`, `time`, `author`, `reason`; рабочий
таймер суммирует интервалы `working` и исключает паузы.

Экран уведомлений сейчас вычисляет сообщения из мок-нарядов: новое назначение,
аварийный наряд, срок ≤30 минут, просрочка, доработка, закрытие. Это **не push** и
не серверная история уведомлений. Подключить FCM и серверный inbox с ID события,
прочтением, датой, типом и ID наряда; открытие ведёт в карточку или результат.

Фото пока передаются как `OrderPhoto` с байтами. API-адаптер загружает их в хранилище
и отправляет ID файлов с временем съёмки и автором. Сжатие выполняет существующий
`PhotoPickerService`; лимит — 5 фото. Для внепланового наряда фото после обязательно.
Черновик уже сохраняет байты фотографий локально на нативных платформах.
Нужны серверная загрузка, её повтор и привязка результатов восстановления
прерванного image_picker к конкретному наряду.

## Что остаётся интеграцией

Настоящая авторизация, серверное хранение и конфликты версий, push и фоновые
напоминания, синхронизация между телефонами, офлайн-очередь сетевых команд и конфликты,
проверка ИИ и расчёт рейтинга. Мок-данные не удалять: использовать их для демо,
тестов и начального наполнения серверной базы.

## Очередь и действия

`ExecutorOrderQueue` показывает текущую работу первой и сортирует очередь по времени
последней постановки в `queued` (история статусов), при равном времени — по номеру.
Приоритет/срок не меняет позицию уже поставленного в очередь наряда.
Номер позиции показывается в списке и карточке. Начало второго наряда блокируется,
пока другой наряд этого исполнителя имеет статус `working`; пауза освобождает работу.
Сервер должен подтвердить этот инвариант и порядок очереди после согласования API.

Форма закрытия сохраняет изменения с задержкой 400 мс и при уходе в фон.
Перед выходом и отправкой ждёт записи; при ошибке сохранения предлагает повтор.
Повреждённый черновик не заменяется пустым: показывается ошибка восстановления.
Внезапное завершение процесса до окончания записи не гарантирует сохранение последнего
символа; поэтому состояние «сохранён» появляется только после завершения записи.

Фото/черновики — локальное хранение формы, а не офлайн-доставка действий и не
постоянное серверное хранилище нарядов. Мок-статусы/наряды пока пересоздаются при запуске.
